# 7. Store seen entry IDs in a JSON file

Date: 2026-09-27

## Status

Accepted

## Context

タイマー型(ADR-0004)なので、どの記事を処理済みかを起動をまたいで覚えておく必要がある。フィードは数十件程度で、1 つのフィードに載る記事も数十件程度。候補は JSON ファイルと SQLite。

- SQLite: 書き込みが壊れにくく、後から項目を足しやすい。一方でクレート(rusqlite)とスキーマの管理が増え、ビルドも重くなる
- JSON ファイル: この規模なら読み書きのコストは無視でき、中身を目で見て確認・修正できる

## Decision

状態は JSON ファイル(既定では `state.json`)に保存する。

- 中身は「フィード URL → そのフィードで処理済みの記事 ID の一覧」
- フィードごとに、処理済みの一覧を「今回フィードに載っていた記事の ID(投稿に失敗したものを除く)」で置き換える。フィードから消えた ID は捨てる
- 設定から消えたフィードの一覧も、起動時に捨てる
- 書き込みは一時ファイルに書いてから rename で置き換え、書き込み中に落ちてもファイルが壊れないようにする
- `state.json` はリポジトリに含めない

## Consequences

- 何年動かしても、ファイルの大きさは「フィードの数 × 1 つのフィードに載る記事の数」で頭打ちになる(数十のフィードで数百 KB 程度)
- 設定から外したフィードを再び追加すると、初回と同じ扱い(ADR-0010)になり、過去の記事は流れない
- 消えた記事がフィードに再び現れると未知の ID になるが、公開日の条件(ADR-0010)で投稿は防がれる
- ETag などを持ちたくなったら、JSON の構造を拡張する
