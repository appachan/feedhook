# 4. Run as a short-lived process on a timer

Date: 2026-09-27

## Status

Accepted

## Context

フィードを定期的に取得する方法として、常駐するプロセスが内部でスケジュールする形(常駐型)と、スケジューラーが短命なプロセスを定期的に起動する形(タイマー型)がある。

- 常駐型の利点: ETag や接続などをメモリに持ち続けられる。フィードごとに間隔を変えたり、分単位より細かく取得したりしやすい。リアルタイムのイベントを受けるならこちらしかない
- 常駐型の欠点: 待機ループやスケジューリングを自前で書く必要がある。長く動くうちに溜まる不具合(メモリ、接続、内部状態の不整合)が起こりうる。落ちたときの再起動も要る(systemd の `Restart=` で済むので、決定的な差ではない)
- タイマー型の利点: コードは「1 回取得して投稿して終わる」だけになり、毎回まっさらな状態で始まる。間隔の変更やログの確認は systemd に任せられる
- タイマー型の欠点: 覚えておくことはすべてファイルに書く必要がある。起動のたびに設定と状態を読むコストがかかる

必要なのは 10 分おき程度のポーリングで、リアルタイム性は要らない。

## Decision

常駐させず、1 回の起動ですべてのフィードを 1 度だけ処理して終了するプロセスにする。定期実行は systemd timer で 10 分おきに行う。

## Consequences

- 状態(既読の記事 ID)はファイルに保存する(ADR-0007)
- 1 回分の処理を関数にまとめておけば、必要になったときに常駐型へ移行できる
- systemd の unit と timer の定義は、デプロイのときに用意する
